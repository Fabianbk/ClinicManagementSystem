# 2. มาตรฐานสถาปัตยกรรมฟอร์ม การเลือกวันที่สองศักราช และระบบแจ้งเตือน (Frontend Form Architecture, Dual-Era Date Picker & Feedback Standards)

## Context

ระบบบริหารจัดการคลินิกมีแบบฟอร์มที่มีความซับซ้อนและมีขนาดใหญ่หลายส่วน เช่น ฟอร์มเวชระเบียนการตรวจรักษา (`RecordTreatmentFormClient.tsx` ความยาวกว่า 2,500 บรรทัด) และฟอร์มลงทะเบียนผู้ป่วยใหม่ (`patients/new/page.tsx` ความยาวกว่า 850 บรรทัด)

ปัญหาที่พบในการใช้งานจริง:
1. **การแจ้งเตือน Error อยู่ไกลจากสายตา**: ฟอร์มเดิมวางกล่องข้อความ Alert ไว้บนสุดของหน้า เมื่อผู้ใช้เลื่อนลงไปกรอกข้อมูลจนถึงด้านล่างสุดแล้วกดปุ่ม "บันทึก" หน้าจอไม่เลื่อนกลับขึ้นไป ทำให้ผู้ใช้ไม่เห็นผลลัพธ์และไม่ทราบว่าเกิดข้อผิดพลาดอะไร
2. **ขาดการแสดงผลข้อผิดพลาดระดับฟิลด์ (Inline Validation)**: เมื่อผู้ใช้กรอกข้อมูลไม่ครบถ้วน ช่อง Input ไม่เปลี่ยนขอบเป็นสีแดง และไม่มีข้อความระบุสาเหตุเล็กๆ ใต้ช่อง ทำให้ต้องเดาว่าช่องใดที่ยังไม่ได้กรอก
3. **การเลือกวันที่ใช้งานยาก (Native Date Picker Limitation)**: การใช้ `<input type="date">` ของเบราว์เซอร์บน Desktop ทำให้การเลือกวันเกิดย้อนหลัง (เช่น ผู้ป่วยสูงอายุที่เกิด พ.ศ. 2480-2510) ต้องคลิกเลื่อนทีละเดือนหลายร้อยครั้ง หรือต้องแปลงเป็น ค.ศ. เพื่อพิมพ์เอง ซึ่งไม่สอดคล้องกับพฤติกรรมของคลินิกแพทย์แผนไทยในไทย
4. **ความเสี่ยงข้อมูลสูญหายและการส่งข้อมูลซ้ำ (Form Vulnerabilities)**: ไม่มีระบบแจ้งเตือนเมื่อออกจากหน้าฟอร์มที่ยังไม่ได้บันทึก (Unsaved Changes) และปุ่มบันทึกบางจุดยังไม่มีการล็อกสถานะ Loading เพื่อป้องกันการกดเบิ้ล (Double Submit)

## Decision

1. **ระบบแจ้งเตือนผลลัพธ์แบบผสม (Toast Notification via Sonner + Smooth Auto-Scroll)**:
   - ติดตั้งและใช้งาน **`sonner`** เป็นไลบรารี Floating Toast Notification หลักของระบบ มีน้ำหนักเบา (<4KB) ลอยแจ้งเตือนสถานะ (สำเร็จ/ข้อผิดพลาด/กำลังประมวลผล) ที่มุมขวาบนอย่างชัดเจนและไม่ถูกบดบัง
   - เมื่อตรวจสอบพบข้อผิดพลาดระดับฟิลด์ ระบบจะทำการ **Smooth Auto-Scroll** เลื่อนหน้าจอไปยังช่องกรอกข้อมูลแรกที่พบข้อผิดพลาด พร้อมโฟกัสเคอร์เซอร์ทันที
2. **คอมโพเนนต์ปฏิทินสองศักราช (Dual-Era Popover DatePicker)**:
   - สร้างคอมโพเนนต์ `<DatePicker>` มาตรฐานของคลินิก แสดงผลในรูปแบบ Popover
   - มี Dropdown เลือกเดือน และปีพุทธศักราช (พ.ศ.) กำกับด้วยปีคริสต์ศักราช (ค.ศ.) ในวงเล็บ เช่น `2567 (2024)` ตัวเลขอารบิกเพื่อความรวดเร็วในการกวาดสายตา
   - รองรับทั้งการคลิกเลือกจากปฏิทิน และการพิมพ์ตัวเลขด้วยคีย์บอร์ดโดยตรง (เช่น `25/10/2535`) พร้อมตัวแปลงเป็นมาตรฐาน ISO `YYYY-MM-DD` อัตโนมัติ
   - รองรับช่วงปีย้อนหลัง 100 ปี ถึงอนาคต 10 ปี พร้อมปุ่มลัด (วันนี้, พรุ่งนี้, +7 วัน, ล้างค่า)
3. **คอมโพเนนต์จัดการฟิลด์มาตรฐาน (`<FormField>`) และ Validation Lifecycle**:
   - สร้างคอมโพเนนต์ `<FormField label="..." required error="...">` ครอบช่อง Input
   - **Validation Lifecycle**: 
     - เมื่อเปิดหน้าจอ: สะอาดตา ไม่มีสีแดง
     - เมื่อคลิกเข้าช่องแล้วคลิกออก (On Blur / Touched) หากยังว่างหรือผิดเงื่อนไข: เปลี่ยนเป็นขอบสีแดง (`border-clinic-danger`) พร้อมแสดงข้อความช่วยเหลือเล็กๆ ใต้ช่องทันที
     - เมื่อผู้ใช้เริ่มพิมพ์แก้ไข (On Change): ล้างขอบแดงออกทันที
     - เมื่อกดบันทึก (On Submit): ตรวจสอบทุกฟิลด์พร้อมกันทั้งหมด และเลื่อนไปยังช่องแรกที่ผิด
4. **มาตรการเสริมความปลอดภัยและความสะดวกในการกรอกข้อมูล (Form Safeguards)**:
   - **Input Masking**: จัดรูปแบบเลขอัตโนมัติสำหรับเลขบัตรประชาชน (13 หลัก: `X-XXXX-XXXXX-XX-X`) และเบอร์โทรศัพท์ (`0XX-XXX-XXXX`)
   - **Prevent Double Submit**: ปิดการทำงานของปุ่ม Submit และแสดง Loading Spinner ทุกครั้งระหว่างรอผลลัพธ์จาก API
   - **Unsaved Changes Protection**: มีการแจ้งเตือนยืนยันก่อนผู้ใช้ปิดแท็บหรือเปลี่ยนหน้า เมื่อมีข้อมูลในฟอร์มที่ยังไม่ได้กดบันทึก
5. **แผนการปรับปรุงแบบ 4 เฟส (4-Phase Rollout Plan)**:
   - **เฟส 1**: สร้าง Core Components (`sonner`, `<FormField>`, `<DatePicker>`, Masking/Scroll utils)
   - **เฟส 2**: ปรับปรุงฟอร์มคนไข้ (`/doctor/patients/new` และ `edit`)
   - **เฟส 3**: ปรับปรุงฟอร์มเวชระเบียนการตรวจรักษา (`RecordTreatmentFormClient.tsx` & `edit`)
   - **เฟส 4**: ปรับปรุงฟอร์มคลังยาและตารางนัดหมาย (`MedicineManagerClient.tsx`, `WeeklyScheduleDialog.tsx`, `PatientBookAppointmentClient.tsx`)

## Considered Options

- **Option A (ที่เลือก)**: พัฒนาคอมโพเนนต์ร่วม `<FormField>` + Dual-Era Popover DatePicker + Toast & Auto-Scroll โดยไม่รื้อโครงสร้าง State เดิม ปลอดภัยต่อโค้ดขนาดใหญ่และได้ผลลัพธ์ตรงเป้าหมายทันที
- **Option B (รื้อฟอร์มทั้งหมดไปใช้ React Hook Form + Zod)**: ถูกปฏิเสธในระยะนี้ เนื่องจากฟอร์มเวชระเบียนมีมากกว่า 2,500 บรรทัดและมี State ซับซ้อนสูง เสี่ยงต่อ Regression บั๊ก
- **Option C (ใช้ Native Datepicker และ Alert แบบเดิม)**: ถูกปฏิเสธ เนื่องจากผู้ใช้งานจริงประสบปัญหาด้านความสะดวกในการเลือกปีเกิดและมองไม่เห็นข้อความแจ้งเตือน
